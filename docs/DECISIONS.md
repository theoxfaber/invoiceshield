# Decisions

## 2026-10-26 22:30 IST — Rules: rebuild the governor (Plan B)
Official rules (Cerebral Valley event guide §4): "New work only: What you present at this Hackathon must have been built during the event… Startups may build on existing products or codebases." We are on the Indie track, so no pre-existing code is reused. The governor is rewritten from scratch in-event.

## 2026-10-26 — Models: open-weight Meta models only
The Meta Model API requires a credit card on file to use the hackathon credits. We built without one, so the stack is Meta's open-weight models: **Muse Glimmer 30B** (Apache-2.0, text + image) as the accounts-payable agent and, in a separate quarantined context, as the document checker; **SAM 3.1** (open weights) for document region masks. Bonus upside: the whole thing can run on an office PC, so invoices need not leave the building.

Day 0 observations (Glimmer on NVIDIA's free trial endpoint): `response_format` JSON schema is accepted but not enforced, so every model output is strictly parsed and anything that fails becomes REVIEW. Image input works (~1 min per invoice image at medium reasoning), so model calls are cached by input hash.

## 2026-10-26 — Fixtures must look plausible
A smoke test showed that an attack invoice with an obviously fake IFSC (containing "FAKE") makes the unshielded agent refuse. That would make the baseline look safer than it is. Attack fixtures therefore use real-format bank details and believable stories, while every name, GSTIN and account stays fictional.

## 2026-10-26 23:30 IST — Fixture identifiers: real format, fictional values
Replaces the pre-event `FAKE`/`7777`/`9999`/`.test` conventions. GSTINs use a ZZ-series PAN with a valid check character; IFSCs use real bank codes (BARB, CNRB, HDFC, ICIC, SBIN, UTIB, KKBK) in each bank's real branch-code shape with made-up branch codes; account numbers have each bank's usual length; domains are plausible `.in`/`.co.in` names. V004 renamed to Visakha Steel Fabricators to avoid RINL's "Vizag Steel" brand. No email is sent and no payment is made to any of these; README carries a "fictional, any match is coincidental" line. The Day 0 smoke showed fake-looking identifiers make the unshielded agent refuse, which would understate the risk.

## 2026-10-26 23:30 IST — Model calls: cache by full-request hash + sample index
Glimmer runs at temperature 1.0, so each eval case is sampled k times (sample = 0..k-1) and each sample cached once. Failed calls are never cached. The demo replays the cache (`offline=True`).

## 2026-10-27 06:00 IST — Baseline agent runs at low reasoning, with a plain AP prompt
Glimmer tool calls on NIM free tier take 25–110 s and "medium" timed out upstream, so the shield-OFF baseline runs at "low", k=3. The prompt is an ordinary AP instruction (pay valid invoices, hold if unsure, reject if not payable) that never mentions fraud, and the agent has no vendor-master tool: it pays what the invoice prints. The harm rule is mechanical and fixed before the run. Realism fixes (today's date in the prompt, CGST+SGST on intra-state invoices) were made after a clean invoice was wrongly held, before any attack was run; no prompt was tuned against attack outcomes.

## 2026-10-27 08:30 IST: Governor treats any extra account/IFSC in the document text as a second set of bank details
The bank box is not the only place a payee can be named; injections paste "the correct account" elsewhere. The assembler extracts every account- and IFSC-shaped value in the text layer and the governor compares each with the master, so a pasted account is a tamper alert (REVIEW) even when the bank box looks right. Cost: a genuine invoice that prints another number shaped like an account (a long reference) would REVIEW; accepted, and it shows up in the false-positive count if it ever happens.

## 2026-10-27 08:30 IST: The shield-ON agent sees a vendor directory (IDs and names), the OFF agent does not
The ON agent needs vendor IDs to propose a payment. This makes ON and OFF differ in more than the payment tool, so the agent's own holds in the ON arm cannot be credited to the shield. The hijacked-agent arm (`eval/run_gate_only.py`) exists to measure the governor without that confound.

## 2026-10-27 08:30 IST: Eval reset endpoint exists only in eval mode
`/v1/eval/reset` returns 404 unless the server runs with `GOVERNOR_EVAL_CLOCK=1`, so samples of one invoice do not trip the duplicate rule. It is never available in a normal run.

## 2026-10-27 11:30 IST: Amount rules are REVIEW-only and check the document against itself and the PO
Three checks: the proposal must equal the printed Total Payable; item lines must sum to it; every non-tax line must name something the PO contracts for (`contracted_items`). They sit in the governor (Rust), fed by deterministic extraction, and can only escalate. Known cost: a PO with several legitimate line types needs those listed or its invoices go to REVIEW; a vendor that words a padded fee with a contracted term ("IT services expedite") would pass, which is why the real protection against over-billing remains the PO balance and tolerance. I02 was fixed after it showed up on the dev set, so it counts as a regression test, never as held-out evidence.

## 2026-10-27 11:30 IST: Slow-drip splits stay a stated limit
Three ₹40,000 invoices 8 days apart are each legitimate-looking and never cross ₹1,00,000 in any 7-day window. The governor pays them. We report this as a deliberate limit instead of widening the window until it breaks genuine monthly billing (benign BS3).

## 2026-10-29: Vendor bank changes need a call-back, two approvers and a cooling-off
Payee binding only holds if the master itself cannot be changed by a forged letter. `governor/src/master_change.rs` refuses a change without a call-back to the number on file, two distinct approvers other than the maker, and 72 h since the request, and audits it. ## 2026-10-30 01:00 IST: Account numbers count only in a bank context (backlog #10)
`all_printed_accounts` used every 9–18 digit run in the text, so phones, IRN/Ack, e-way bill, PO/order/reference numbers and UTRs could raise the tamper alert on a genuine invoice. Now a digit run is an account only when its own field label, or the nearest label before it, is a bank one (A/c, Account, Beneficiary, Bank, IFSC, SWIFT, remit, pay to, NEFT/RTGS…), or when an IFSC/SWIFT code follows it on the same line, or when it has no label and bank words or a bank code are close by. Non-bank labels (Ph, GSTIN, PAN, IRN, Ack, PO, Invoice, Ref, UTR, PIN, MICR, routing…) and any other `<label>:` field exclude it unless an IFSC follows. The bank box is labelled, so it is always read; injected payees written in bank words or next to an IFSC still raise the alert (all dev and variant verdicts unchanged). Accepted gap: an account disguised under a non-bank label with no bank code beside it raises no alert; it still cannot be paid, because the payee comes only from the master.

## 2026-10-30 01:30 IST: What we changed after seeing the clean-invoice results, and what we did not
The first false-positive run (38/60 PAY on the gate path) exposed two extraction bugs, fixed with tests and with both runs kept: labelled reference fields outside the label vocabulary were treated as unlabelled numbers, and the item-table parser could not read a multi-column (HSN / qty x rate) table or negative amounts. We did **not** change the `charge_not_on_po` rule for "Round off" lines although it caused every remaining false positive: that is a policy choice, and changing it after seeing the set would make the number meaningless. A fresh-seed set was generated and run once after the fixes to give a less-tuned figure.

## Fri Oct 30: round-off rule NOT changed
The 2–4 "Round off" REVIEWs on clean invoices (charge_not_on_po) stay as measured. Rules are frozen as of now; the held-out run uses the current engine. Reported as a known false-positive source (about 2/60 to 4/60), not quietly fixed.

## 2026-10-30 18:45 IST: Duplicate payment is blocked by the database, not only by a mutex (Phase 3)
Before, one `tokio::Mutex` around evaluate + ledger write was the only thing stopping two copies of an invoice from both passing the duplicate check. That holds inside one process and nowhere else: a second server process, a restart that lost the in-memory ledger, or a future code path that writes the ledger without the lock would each pay twice. Now state lives in SQLite (WAL) and the guarantee is in the database: every action is one `BEGIN IMMEDIATE` transaction (the write lock is a file lock, so it serialises processes too), the in-memory ledger is reloaded inside that lock when another connection has committed, and partial UNIQUE indexes on live ledger rows, `(vendor_id, invoice_key, amount_paise, currency)` and `(irn)`, make a second live entry impossible even if the engine were bypassed. A write the DB refuses returns 409 and is never reported as paid. We kept the in-process mutex as defence in depth (it also avoids pointless lock contention inside one process). Cost: writes are serialised per DB file (fine for AP volumes; measured in tests at 40 concurrent requests across two processes) and the engine still holds the ledger and audit chain in memory, reloaded on change. Verdict rules are unchanged; the indexes only enforce what `duplicate_invoice` / `duplicate_irn` already decide. Currency is part of the key so the Phase 1 currency work slots in without a schema change (INR when absent).

## 2026-10-30 18:45 IST: Audit chain is anchored with an Ed25519-signed head, verified against a pinned key
A hash chain stored next to the data cannot detect someone who rewrites the whole chain and recomputes every hash. The server periodically signs (seq, head hash, time) and appends it to an append-only file outside the DB, optionally POSTing it elsewhere; `governor verify` checks the chain against every anchor under a pinned public key. The local file only protects against DB-only tampering; real external anchoring needs `GOVERNOR_ANCHOR_URL` (or shipping the file) to a system the operator of the DB does not control. Plain http only for the POST, to avoid a TLS client dependency; use a relay. Key from env/file, never committed; tests generate one at runtime.

## 2026-10-30 18:45 IST: Eval runs stay in memory unless told otherwise
`GOVERNOR_DB` defaults to `governor.db`, but to `:memory:` when `GOVERNOR_EVAL_CLOCK=1`, so the Python eval harness and replays behave exactly as before (fresh state per run, `/v1/eval/reset` clears the tables). Production must set `GOVERNOR_DB` to a durable path.

## Fri Oct 30, 18:40 IST: Round-off rule CHANGED, before any held-out run (supersedes the 08:20 "not changed" entry)
The production-hardening pass (docs/HARDENING.md, Phase 1) reopened the rules; the frozen held-out set has still not been generated or run, so a rule change now does not contaminate it. Rule, decided and written here before re-running anything: a **non-tax** item line whose description is exactly "Round off", "Rounding" or "Round-off" (case-insensitive, punctuation/spacing ignored, so "ROUND OFF:" and "Roundoff" count; "Round off adjustment fee" does not) and whose |amount| is **under one unit of the invoice currency (100 minor units: ₹1.00 = 100 paise)** is not a charge and is exempt from `charge_not_on_po`. Everything else about the line is unchanged: it still counts toward "lines add up to the printed total". A round-off of ₹1.00 or more, or any other wording, still REVIEWs.
Why: backlog #15. On the clean sets every invoice that printed a round-off line went to REVIEW (4/60 seed 20261030: C09 C13 C28 C43; 2/60 seed 20261101: C04 C56) and no other invoice did; most Indian GST invoices round to the rupee, so the old rule makes a human look at a large share of genuine invoices for paise. The exemption cannot move money: a line under ₹1 cannot fund an over-payment, and the printed total must still equal the proposal and the sum of the lines. The 4 + 2 known REVIEWs are expected to become PAY; that expectation is the reason for the change, so the clean-set numbers after it are reported as "after a rule change made with the set's results known", not as an independent false-positive rate. Implemented as `engine::is_round_off`.

## Fri Oct 30, 18:40 IST: Currency is modelled; amounts are minor units of an ISO 4217 code (backlog #6)
Proposal (`currency`, default INR), PO (`currency`, default INR) and extracted evidence (`currency` + `all_currencies`, from ₹/Rs/INR, $/US$/USD, €/EUR, £/GBP, AED, S$/SGD markers) each carry a currency. The governor REVIEWs (`currency_mismatch_invoice`, `currency_mismatch_po`, `currency_ambiguous`, `unknown_currency`) on any disagreement, on a document naming two currencies, and on a currency the policy has no limits for; PO balance, approval threshold, payout cap and the 7-day vendor window are compared only within one currency (ledger entries carry their currency). `amount_paise`/`open_balance_paise` keep their names for compatibility and now mean minor units. INR limits are unchanged; USD limits are the INR ones at the eval rate 84.00 rounded down to whole dollars ($1,190 approval, $5,952 cap) so USD is never looser. V003's PO is now what the master comment always said it was: USD 1,000.00 open (100000 cents), not ₹84,000 in paise. A document with no currency marker is assumed INR. The shield-ON agent's payment tool still has no currency argument, so an agent proposing a USD invoice sends no currency, the governor reads INR, and the payment goes to REVIEW: the safe failure. Adding the argument changes the prompt (cache miss); left for later.

## Fri Oct 30, 18:40 IST: Structured PO lines replace the substring match (backlog #8)
`contracted_items` (case-insensitive substring of the line description) is gone; a "Consulting fee - totally not cleaning" line passed it because "cleaning" was in it. A PO now has `lines` (item, aliases, qty, unit_price_minor, currency, unit). A non-tax invoice line must name a PO line (the description equals the item or an alias, starts with it as whole words, or ends with it in brackets; a word in the middle never matches) in the invoice's currency, and must fit it: for a rate line, qty x unit price must reproduce the line amount (±1 minor unit per unit), the unit price must be <= the PO rate (+`policy.line_price_tolerance_bp`, default 0) and the quantities billed against the line on that invoice must be <= its qty; for a lump-sum line (`unit: "lot"`) the lines billed against it must add up to <= qty x unit price. Anything unmatched or over → `charge_not_on_po` REVIEW. Lines without a printed qty/rate are read as 1 x amount. The fixture POs were migrated to one lump-sum line per former contracted item, capped at the PO's open balance, because the fictional invoices were generated against PO categories, not rate contracts; so on the fixtures the line rule is "names a PO line + under the line cap", and the qty x rate protection is shown by tests with rate lines, not by the dev set. Known limit: quantities and values are checked per invoice, not cumulatively across invoices (the PO open balance remains the cumulative bound).
## Fri Oct 30 18:40 IST: Evidence is signed by a separate extraction service (Phase 2, trust boundary)
External review: `/v1/actions` accepted `evidence` from whoever called it, so a compromised agent process could send an empty `printed_bank_account` and the right GSTIN. Now:
- **Who extracts.** `extractor/` is its own process (`python -m extractor.service`) and the only holder of an Ed25519 signing key (in memory for tests/demo; a gitignored 0600 PEM via `--key-file` otherwise; never committed). It takes the raw PDF bytes (+ cover email), extracts with the unchanged `assembler/extract.py` + `evidence.py` inside a sandbox, and returns `{"payload": <canonical JSON, sorted keys, no whitespace>, "sig": <base64>}`. The payload carries `v`, `key_id`, `doc_sha256` (computed by the service from the bytes it received), `email_sha256`, `extractor_version`, `issued_at`, a 128-bit `nonce`, `status` and the evidence.
- **What the governor checks** (`governor/src/trust.rs`): key id known, signature verifies (`verify_strict`) over the exact payload bytes, payload schema, freshness against the real wall clock (max age 300 s, skew 30 s; the eval clock header never applies), nonce unused (bounded store, pruned past max age; full store fails closed), proposal's `document_sha256` equals the signed hash, extraction status ok. Only then are the signed values handed to the unchanged rules.
- **REVIEW vs BLOCK.** BLOCK when only tampering explains it: `evidence_signature_invalid` (bad/garbled signature, unknown key, edited payload), `document_hash_mismatch` (evidence for another document), `evidence_replayed`. REVIEW when an honest fault is plausible: `evidence_unsigned` (no envelope, e.g. an old client; any raw `evidence` is never read), `evidence_stale`, `evidence_from_future`, `document_hash_missing`, `evidence_payload_invalid`, `extraction_failed`, `evidence_nonce_store_full`. Nothing is paid either way.
- **Dev mode.** `GOVERNOR_DEV_UNSIGNED_EVIDENCE=1` restores the old caller-supplied path for unit tests that hand-build evidence; off by default, logs a warning, and the server refuses to start with it unless `GOVERNOR_EVAL_CLOCK=1`. `GOVERNOR_EXTRACTOR_PUBKEY` is required otherwise.
- **Hostile documents.** Extraction runs in a subprocess: input ≤ 10 MB and must look like a PDF (checked before spawning), ≤ 50 pages (declared `/Count` checked before the page-tree walk, then the walk), RLIMIT_CPU 30 s (per process; OCR runs tesseract as a child), RLIMIT_AS 1.5 GiB, RLIMIT_FSIZE 64 MB, RLIMIT_NOFILE 256, no core, 60 s wall clock (a photo invoice OCRs in ~20 s on this loaded sandbox) with SIGKILL of the process group, 4 MB stdout cap, empty environment (no API keys), fresh user+network namespace (no network; verified on this sandbox) plus Python sockets disabled in the worker. Any failure is signed as `status: failed` → REVIEW.
- **Verdict rules unchanged.** The signed path feeds the same `Evidence` struct to the same engine; the cached Day 1 replays and the gate-only run give identical verdicts and reasons (eval/results/*_signed_2026-10-30.jsonl, *_rerun_2026-10-30.jsonl). One normalizer fix came out of fuzzing: `normalize::invoice_no` is now iterated to a fixpoint, because uppercasing after NFKC left "ΐ" decomposed so its composed twin got a different duplicate key. No eval case is affected.
- **With Phase 3's durable store.** `persist::Store` carries the `TrustVerifier`; the server always sets it, so every `/v1/actions` body goes through provenance checks inside the same transaction path. Used nonces live in process memory only: after a restart, or across two governor processes on one DB, an envelope younger than 300 s could be evaluated once more. It still cannot pay twice, because the ledger dedupe (DB UNIQUE) blocks the second payment; persisting nonces in the DB is the follow-up. Phase 3's process-level durability tests send hand-built evidence, so they run on the documented test-only unsigned path; the signed path through the server is covered by `tests/test_trust_boundary.py`.
- **What this does not solve (stated limits).** (1) The signature proves the extractor read *this document*; it does not prove the document is the one the vendor emailed. Whoever feeds the extractor (here the pipeline's ingestion step) must take documents from the mailbox, not from the agent; production should have the extractor pull by message id. A compromised orchestrator that can submit its own PDF to the extractor can get honest evidence for a document it wrote, which then still has to pass every rule against the vendor master (payee from master, GSTIN, domain, PO, amounts). (2) Proposal fields the agent chooses (vendor, invoice no, amount, PO) are still bound to the document only through the existing rules (printed total, GSTIN, domain). (3) Signing key protection is OS-process isolation only; an HSM/KMS is the production step. (4) The cover email is hashed into the payload but its authenticity (DKIM) is not checked.

## Fri Oct 30, 20:20 IST: The shield-ON agent names the payment currency
Follows the 18:40 currency decision. The ON agent's `propose_payment` tool now has an optional `currency` argument (ISO 4217; the schema and prompt say "INR unless the invoice is in another currency"), and `amount_paise` is described as minor units of that currency. Python records `"INR"` when the agent omits it (the governor's own default) and otherwise passes the agent's value through untouched; the governor normalizes it and still REVIEWs any disagreement with the PO or the document, or an unknown code. Why: without it every USD invoice went to REVIEW on the model path (5/60 clean). Why this is safe: the currency is one more agent claim the governor checks against two independent sources (the PO in the master, the extracted document), and amounts are never compared across currencies; an agent that lies about currency gets REVIEW, not a looser limit (USD limits are set at or below the INR ones). The OFF baseline is left unchanged on purpose, so the OFF/ON comparison still differs only in the payment tool's trust model. Cost: the prompt change invalidated the ON agent cache, so the dev ON arms were re-sampled; per-sample outcomes moved among hold / REVIEW / BLOCK, none to a payment (EVAL_LOG.md, Oct 30 ~20:15).

## Fri Oct 30, 21:20 IST: Per-identity keys and roles; the agent can never approve (Phase 4)
Before, one shared API key could call every route except resolve, and resolve took a free-text `approver` string from the body, so "maker-checker" was a convention. Now every caller is an identity with roles (`agent`, `operator`, `approver`) from `GOVERNOR_IDENTITIES[_FILE]`, which holds only SHA-256 hashes of random 256-bit keys (`governor new-key`); a fast hash is enough because the keys are not passwords. The agent role cannot be combined with any other role (startup refuses), so a hijacked agent or a stolen agent key cannot approve, enter a bank change or confirm a call-back. Maker-checker binds to the authenticated identity: the proposer of a payment cannot resolve it, the maker of a bank change cannot confirm its call-back or approve it; each is enforced in code and by a DB trigger. The approver recorded is the identity, never the body. The legacy single keys keep working (`GOVERNOR_API_KEY` → agent, `GOVERNOR_OPERATOR_KEY` → operator + approver, warned) so the eval harness and old deployments are unchanged. `/v1/audit/verify` and `GET /v1/decisions/:id` stay readable by any identity (read-only). Phase 6's validated `config.rs` now carries these settings (`security::SecurityConfig`), so every Phase 4 variable is checked at startup with the rest (all errors listed, exit 2).

## Fri Oct 30, 21:20 IST: Vendor bank changes go through the server; cooling-off counts from the second approval (Phase 4)
The library rule (call-back to the number on file, two distinct approvers who are not the maker, cooling-off, audit) is now an HTTP workflow persisted in SQLite (schema v2). Numbers on file come from a separate trusted file (`GOVERNOR_VENDOR_PHONES`), not the master schema. The cooling-off (default 72 h, kept from the 2026-10-29 decision rather than the 24 h floated in the Phase 4 brief; configurable) starts at the second approval, not at the request, so a request cannot be pre-filed to make a later approval effective at once. A change is applied inside the first write transaction whose clock (the eval clock when it is on) has passed `effective_at`; until then the master holds the old details, so the unchanged engine keeps REVIEWing invoices that print the new ones and no payment to them can be ALLOW. A call-back to another number is refused and audited; a call-back where the vendor confirms different details rejects the change. The call-back is an attestation by an authenticated identity, not a verified phone event (THREAT_MODEL.md). No verdict rule changed.

## Fri Oct 30, 21:20 IST: Applied bank changes are MAC'd; a forged one blocks the vendor instead of redirecting it (Phase 4)
Persisting bank changes in the DB created a new path: a DB-only attacker could insert an `applied` row and the master would be rebuilt with their account. Each applied change now carries HMAC-SHA256 (hand-rolled over `sha2`, RFC 4231 vector tested) under `GOVERNOR_STATE_KEY`; at load, a row without a valid MAC is not applied and that vendor is removed from the effective master, so every payment to it BLOCKs `unknown_vendor` and the log says why. Blocking rather than silently ignoring the row: ignoring would keep paying the old account, which is safe against redirection but hides that someone wrote to the DB. Without the key (warned at startup) the protection is off; stated in the threat model.

## Fri Oct 30, 21:20 IST: Rate limits on by default in production, off by default in eval mode; TLS optional via rustls/ring (Phase 4)
Token buckets per client IP (200 req/s, burst 400), per identity (100 req/s, burst 200) and for failed authentications per IP (30/min, burst 10); 429 with `Retry-After`; in-memory and per process, bounded map that fails closed when full. In eval mode (`GOVERNOR_EVAL_CLOCK=1`) the defaults are off unless set, like the in-memory DB default, so replays and the Phase 6 load test measure the gate; the 429 tests set them explicitly. TLS uses rustls with the `ring` provider (no aws-lc/cmake in the build), PEM files via `GOVERNOR_TLS_CERT_FILE`/`_KEY_FILE`, served through hyper-util so the same router (with Phase 6's metrics middleware) runs with or without TLS; a bad pair stops startup. `X-Forwarded-For` is not trusted. Every Phase 4 secret also accepts `*_FILE` (setting both is an error; loose file permissions are warned). Dependency check: `cargo audit` against the RustSec DB is clean; an OSV query over Cargo.lock additionally reports GHSA-qwgh-2vcv-g2f7 in `block-buffer 0.10.4` (via `sha2 0.10`, pre-existing, not in RustSec, judged unreachable: no panic is caught around hashing); noted in THREAT_MODEL.md.

## Fri Oct 30, 22:10 IST: Near-duplicate rule for suffixed re-submissions (red-team R4), decided before any eval re-run
Finding R4 (docs/RED_TEAM_INTERNAL.md): the same invoice re-sent as `…/0900-A` was ALLOWed, because the duplicate key is vendor + normalised number and a suffix makes a new key. Rule, written here before re-running anything:
- `normalize::near_dup_base(no)` removes **one** trailing re-submission suffix, right after a digit: 1-3 letters with an optional separator (`INV-101A`, `INV-101-A`, `0900/REV`) or a separator plus 1-2 digits (`INV-101-1`, `INV-101/02`). Digits glued on without a separator are never stripped (`INV-1011` is not `INV-101`), nor are 4+ letters or 3+ digits. The base is then normalised exactly like the duplicate key.
- **REVIEW `near_duplicate_invoice`** (STRUCTURAL) when a live (paid or pending) ledger entry has the same vendor, the same amount and currency, is inside a **90-day** look-back (`policy.near_duplicate_window_secs`, default 7,776,000 s), and one number is the other plus such a suffix (either direction: base of the new number = old key, or base of the old number = new key). It runs only when the exact-duplicate (BLOCK) and same-number-other-amount (REVIEW) rules did not fire.
- **REVIEW, not BLOCK**: real vendors do reissue corrected invoices as `-A`/`-R`/`-1`; a human must decide which one is payable. Same amount only: a different amount is a supplementary or corrected bill, which the PO balance and the amount rules already bound. 90 days, not the 7-day split window: re-submission fraud is usually weeks later, and a 90-day duplicate look-back is common AP practice; beyond that the exact-key BLOCK still holds forever.
- Persistence: each ledger entry stores its `near_key` inside the entry JSON the SQLite store already persists, so the rule survives restarts with no schema change. Entries written before this change have no `near_key`; for them only the "new number = old number + suffix" direction applies.
- Known cost: a vendor that numbers genuinely different invoices `INV-101`, `INV-101A`, `INV-101B` at the same amount within 90 days gets a REVIEW. Known gap: a re-submission under an unrelated new number is still only caught by the split window and the PO balance (no PDF-hash check; the signed `doc_sha256` would be the next step).

## Fri Oct 30, 22:10 IST: Look-alike characters in bank fields are tampering (red-team R6), decided before any eval re-run
Finding R6: an IFSC printed with a Cyrillic `В` was invisible to the ASCII-only `IFSC_RE`, so the extractor reported no IFSC and no tamper alert was raised. Rule:
- **Extractor** (`assembler/extract.py`, `confusable_bank_tokens`): a token that is not plain ASCII but folds (NFKC, invisible marks removed, a fixed Cyrillic/Greek look-alike table, `О` in the fifth slot read as `0`) into an IFSC shape, or into a 9-18 digit account in a bank context (same `classify_number` context rules as ASCII accounts), is added to `all_printed_ifscs` / `all_printed_accounts` **as printed**. It is never repaired into a usable value.
- **Governor** (rule 9): any printed account or IFSC value containing a non-ASCII or control character sets the tamper alert and REVIEWs, with the detail "contains non-ASCII look-alike characters". Rule name `bank_details_differ_from_master` when the values also differ from the master (one reason, not two, so the same field is not double-counted), `bank_details_non_ascii` when the ASCII digits alone would have matched (`digits()` drops a Cyrillic `О` inside an account, which previously looked like a match).
- Consistent with existing tamper handling: a tamper alert alone is REVIEW; tamper plus any other REVIEW/BLOCK reason escalates to BLOCK (design §4a). The payee still comes only from the vendor master, so this changes alerts and verdicts, never who is paid.
- GSTIN look-alikes are unchanged (already not read → REVIEW unreadable, or BLOCK when sent directly).
